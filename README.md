# Telegram MCP Publisher

MCP-сервер для безопасной публикации подготовленных ChatGPT/Codex материалов в
один или несколько Telegram-каналов. Сервер поддерживает обычные посты,
изображения, Telegram Rich Messages, предварительный просмотр, защиту от
повторной отправки и запланированную публикацию по серверной политике.

Версия 4.0 может работать в двух конфигурациях:

- локальный однопользовательский режим с секретным MCP URL;
- мультитенантный режим с PostgreSQL и внешним OAuth/OIDC-провайдером.

Production-конфигурация конкретного сервера и приватные планы развития в эту
публичную ветку намеренно не входят.

## Возможности

- `list_channels` возвращает доступные текущему пользователю каналы.
- `upload_image` принимает JPEG, PNG или WebP в base64 и сохраняет файл во
  временном приватном хранилище.
- `preview_digest` нормализует разметку, проверяет лимиты и сохраняет неизменяемый
  серверный предпросмотр с SHA-256.
- `publish_digest` публикует только сохранённый предпросмотр по
  `previewId + previewSha256`.
- Целевые каналы входят в контрольную сумму и не могут быть заменены между
  предпросмотром и публикацией.
- Идемпотентность блокирует случайную повторную отправку одинакового содержимого.
- При отправке в несколько каналов результат сохраняется отдельно для каждого
  канала; частичный или неоднозначный результат нельзя автоматически повторять.
- Загруженные изображения удаляются после попытки публикации, а неиспользованные
  файлы очищаются по TTL.

## Форматы публикации

`classic` используется по умолчанию. Он преобразует поддерживаемую Markdown-
разметку в Telegram HTML. Обычное сообщение ограничено 4096 символами; одна
обложка отправляется через `sendPhoto`, поэтому её подпись ограничена 1024
символами.

`rich` сохраняет Telegram Rich Markdown и отправляет `sendRichMessage`. В нём
доступны заголовки, списки, таблицы, цитаты, сворачиваемые блоки, формулы и до 50
изображений внутри текста. Общий лимит — 32768 символов.

Локально созданное изображение сначала передаётся в `upload_image`. Полученный
непрозрачный `source` затем используется без изменений:

```json
{
  "markdown": "# Заголовок\n\n{{image:cover}}\n\nТекст публикации.",
  "publicationFormat": "rich",
  "channelIds": ["channel-id-from-list-channels"],
  "images": [
    {
      "id": "cover",
      "source": "mcp-upload:opaque-temporary-id.png",
      "caption": "Подпись",
      "spoiler": false
    }
  ]
}
```

Локальный путь и `file://` не поддерживаются: удалённый MCP-сервер не может
прочитать файл с компьютера клиента. Публичный HTTPS URL и уже известный Telegram
`file_id` также можно использовать как источник.

## Требования

- Node.js 20 или новее;
- pnpm 11;
- Telegram-бот с правом публикации в выбранных каналах;
- PostgreSQL и внешний OAuth/OIDC-провайдер — только для мультитенантного режима.

## Установка и проверка

```bash
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env
pnpm run check
pnpm test
pnpm start
```

Тесты не обращаются к Telegram и ничего не публикуют: Bot API заменён локальной
имитацией.

## Локальный режим

Минимальная конфигурация:

```dotenv
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHANNELS_JSON='{"News":"@demo_channel","News test":"-1001234567890"}'
TELEGRAM_DEFAULT_CHANNEL=News
MCP_ACCESS_KEY=длинное_случайное_значение
ALLOW_SCHEDULED_PUBLISH=false
```

Ключ можно создать командой `openssl rand -hex 24`. После запуска MCP будет
доступен по адресу:

```text
http://localhost:8787/mcp/<MCP_ACCESS_KEY>
```

Не передавайте Telegram-токен клиенту MCP и никогда не добавляйте `.env` в Git.
Если серверу нужен прокси только для Telegram Bot API, задайте
`TELEGRAM_PROXY_URL` с HTTP(S)-адресом прокси.

## Мультитенантный режим

Если задан `DATABASE_URL`, сервер использует PostgreSQL и единую конечную точку
`/mcp`. Доступ проверяется по Bearer JWT внешнего OAuth/OIDC-провайдера. Сервер
проверяет подпись через JWKS, точные `iss` и `aud`, срок действия, `jti`, отзыв и
области доступа.

Основные переменные:

```dotenv
DATABASE_URL=postgres://publisher:password@localhost:5432/publisher
PUBLIC_BASE_URL=https://publisher.example.com
OAUTH_ISSUER=https://auth.publisher.example.com
OAUTH_JWKS_URI=https://auth.publisher.example.com/.well-known/jwks.json
OAUTH_JWT_ALGORITHMS=RS256
OAUTH_REQUIRE_JTI=true
ONBOARDING_TOKEN_PEPPER=...
TELEGRAM_WEBHOOK_SECRET=...
```

`OAUTH_AUDIENCE` должен точно совпадать с
`https://publisher.example.com/mcp`; если он не задан, сервер выводит его из
`PUBLIC_BASE_URL`. В production OAuth URL должны использовать HTTPS.

Примените миграции отдельно от запуска приложения:

```bash
pnpm db:migrate
pnpm start
```

Периодическую очистку базы выполняет:

```bash
pnpm db:cleanup
```

Сервер авторизации и конкретная инфраструктура развёртывания намеренно не входят
в проект. API подключения пользователей, Telegram-каналов и политик автоматизации
описан в [docs/ONBOARDING_API.md](docs/ONBOARDING_API.md).

## Подключение Telegram

1. Создайте бота через [@BotFather](https://t.me/BotFather).
2. Добавьте его администратором канала с правом публикации.
3. В локальном режиме внесите разрешённые каналы в `.env`.
4. В мультитенантном режиме используйте onboarding API и настройте Telegram-
   вебхук командой `node scripts/configure-telegram-webhook.mjs`.

В мультитенантном режиме модель видит внутренние ID только своего рабочего
пространства и не получает Telegram `chat_id` или токен бота.

## Подключение MCP

Для удалённого подключения MCP должен быть доступен по публичному HTTPS-адресу.
После добавления сервера к ChatGPT/Codex можно использовать такой запрос:

> Вызови `list_channels`, подготовь пост и сделай `preview_digest` для выбранных
> каналов. Ничего не публикуй без моего подтверждения. После подтверждения вызови
> `publish_digest` только с возвращёнными `previewId` и `previewSha256`.

Для запланированного запуска используйте отдельные учётные данные и серверное
разрешение на автономную публикацию. Задача должна вызвать `list_channels`, затем
`preview_digest`, после чего `publish_digest` с `publicationMode="scheduled"` и
`allowDuplicate=false`. При `partial`, `failed` или неоднозначной сетевой ошибке
автоматический повтор запрещён.

## Безопасность

- Храните `.env`, токен бота, ключи OAuth и конфигурацию прокси вне репозитория.
- Не публикуйте секретный MCP URL локального режима.
- Ограничивайте доступные каналы серверной конфигурацией или рабочим пространством.
- Для production используйте HTTPS, PostgreSQL и короткоживущие OAuth-токены.
- Не включайте `ALLOW_OPAQUE_BOOTSTRAP_AUTH` за пределами краткой миграции.
- Перед обновлением запускайте `pnpm audit --prod`, `pnpm run check` и `pnpm test`.

## Docker

В репозитории есть минимальный `Dockerfile` приложения. Конкретные Compose,
reverse-proxy, OAuth и release-конфигурации зависят от окружения и должны
создаваться отдельно.
